# REAL-WORLD NEED RADAR — METHODOLOGY v1.1
## Environment / parameter dependence control
Date: 2026-08-23

## Why this section exists

Two independent scans were run to test whether Radar output is being shaped by the working environment, current project context, or explicit scan parameters.

The comparison shows that three different sources of bias must be treated separately:

```text
ENVIRONMENT / CONTEXT BIAS
!=
PARAMETER / QUERY BIAS
!=
SOURCE-DENSITY BIAS
```

A scan is not independent merely because it was started in a different chat or task. Independence must be demonstrated by controlled variation.

## Current conclusion

The evidence does NOT support the strong claim:

```text
THE RADAR IS MAINLY MIRRORING THE PROJEKTOR ENVIRONMENT
```

because under anti-bias and diversity constraints the winning opportunities moved clearly outside the Projektor-native domain.

However, the comparison DOES show that output is highly sensitive to:

```text
SEARCH CONSTRAINTS
SOURCE MIX
CATEGORY GUARDRAILS
VALIDATION RULES
```

Therefore:

```text
RADAR OUTPUT
= FUNCTION OF WORLD EVIDENCE
+ SEARCH DESIGN
+ SOURCE ECOLOGY
+ QUALIFICATION RULES
+ POSSIBLE CONTEXT EFFECT
```

The possible context effect has not been fully eliminated, but it is no longer the best explanation for the observed results.

## Source-density bias

GitHub is not a neutral sample of human problems.

GitHub disproportionately exposes:

- bugs;
- infrastructure failures;
- developer tooling;
- self-hosted systems;
- compatibility problems;
- API/auth issues;
- technical workarounds.

Therefore a broad scan using Reddit + GitHub without category balancing can naturally become technical even without any hidden Projektor influence.

This must be classified as:

```text
SOURCE-DENSITY BIAS
```

not automatically as environment contamination.

Reddit broadens the observable problem space, but subreddit/query selection can create its own density bias.

---

## Methodology fingerprint

Even when the subject matter changes, both scans show a stable ranking preference for problems with:

```text
REAL PAIN
+ REPEATED FAILURE
+ CURRENT WORKAROUND
+ MONEY / ECONOMIC CONSEQUENCE
+ EXISTING SOLUTION
+ OBSERVED FAILURE OF THAT SOLUTION
```

This is expected.

It is a methodology fingerprint, not necessarily an environment leak.

The Radar is intentionally biased toward:

```text
"people already try to solve this and still fail"
```

rather than:

```text
"this sounds novel"
```

That bias should be preserved.

---

## Cross-run recurrence

A repeated topic across otherwise different scans is self-hosted photo backup / Immich.

That recurrence is valuable because it arose under different portfolio compositions.

But recurrence alone still does not prove a standalone business.

One run framed it as a possible backup continuity opportunity; another correctly downgraded it as primarily a product-defect cluster because WTP for a separate product was not found.

Therefore cross-run recurrence should increase:

```text
PROBLEM CONFIDENCE
```

but must NOT automatically increase:

```text
OPPORTUNITY CONFIDENCE
```

---

## New mandatory distinction

The comparison makes this separation mandatory:

```text
PROBLEM CONFIDENCE
= how confident are we that the pain is real?

OPPORTUNITY CONFIDENCE
= how confident are we that a monetizable residual gap is real?
```

These must be separate fields in every future Evidence Package.

Examples:

```text
Immich backup:
PROBLEM CONFIDENCE = HIGH
OPPORTUNITY CONFIDENCE = LOW

Crosslisting / inventory reconciliation:
PROBLEM CONFIDENCE = HIGH
OPPORTUNITY CONFIDENCE = HIGHER / VALIDATION CONTINUES
```

This prevents repeated product defects from being mislabeled as markets.

## Environment-independence test protocol

To test whether the Radar is influenced by the environment, use paired or triplicate runs.

### Freeze these variables

```text
TIME WINDOW
SOURCE SET
EVIDENCE SCHEMA
MINIMUM HUMAN SIGNAL COUNT
WTP DEFINITIONS
DEEP-VALIDATION PROCEDURE
KILL RULES
```

### Deliberately vary only one factor

Examples:

```text
RUN A:
current project environment

RUN B:
clean / unrelated environment

RUN C:
same clean environment + explicit anti-bias constraints
```

or:

```text
RUN A:
unconstrained categories

RUN B:
diversity guardrails

ALL OTHER RULES IDENTICAL
```

Do not change multiple variables and then attribute differences to only one cause.

---

## What to measure between independent runs

Future paired scans should report:

```text
EXACT CLUSTER OVERLAP
SEMANTIC MECHANISM OVERLAP
TOP-3 OVERLAP
CATEGORY DISTRIBUTION
SOURCE DISTRIBUTION
PROBLEM-CONFIDENCE AGREEMENT
OPPORTUNITY-CONFIDENCE AGREEMENT
WTP AGREEMENT
DEEP-VALIDATION RANK CHANGES
```

Recommended interpretation:

```text
same exact opportunity in multiple independent runs
→ stronger recurrence evidence

different opportunities but same failure mechanism
→ methodology / source pattern may be stable

completely different top portfolios after parameter change
→ parameter sensitivity confirmed

same Projektor-native concepts despite strong anti-bias controls
→ investigate environment/context contamination
```

## Controlled baseline run

A future benchmark should use a frozen prompt that contains no domain quotas and no project-native vocabulary.

Example:

```text
HORIZON:
last 30 days

SOURCES:
Reddit + GitHub

REQUIRE:
real Human pain
minimum 2 independent signals for high confidence
workaround evidence
WTP evidence or UNKNOWN
existing solutions
why they fail
separate problem confidence
separate opportunity confidence

DO NOT:
optimize for any named industry
search Projektor-native terms
force AI/devtools
force startup novelty
```

Run the exact same prompt in multiple isolated contexts.

This is the cleanest test of environment dependence.

```text
= CLEARLY SUPPORTED

```

The second scan is particularly important because it distinguishes:

1. pain + direct WTP + persistent failure → opportunity candidate;
2. pain + spend only through a larger suite → validation candidate;
3. pain + measurable economic impact + crowded category → plausible niche;
4. strong pain but solution already works → do not overvalue;
5. repeated bug / feature gap → do not automatically call it a business.

This classification should be retained permanently.

## Decision rule

Do not ask:

```text
"Did two scans return the same ideas?"
```

Ask:

```text
"Under controlled changes,
what remained stable,
what changed,
and which variable best explains the change?"
```

The purpose of independent scans is not to force identical output.

The purpose is to determine whether the Radar is:

- world-sensitive;
- parameter-sensitive;
- source-sensitive;
- or context-contaminated.

At present, the evidence indicates a healthy mixture of world evidence + parameter sensitivity, with no strong proof that the Projektor working environment dominates the scan.
